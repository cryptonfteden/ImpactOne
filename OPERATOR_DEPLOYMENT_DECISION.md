# OPERATOR_DEPLOYMENT_DECISION.md — Phase HOSTING-DECISION-001

## Recommended provider
**Render** (primary). **Railway** (fallback, if Render is unavailable or the founder prefers pure usage-based billing).

## Frontend service
Render **Static Site** — build command `cd frontend && npm ci && npm run build`, publish directory `frontend/dist`. Free. Purpose-built for a static SPA/PWA: global CDN, automatic TLS, custom domains, no server to manage.

## Backend service
Render **Web Service**, **Starter** instance ($7/month, 512MB/0.5 CPU, no idle sleep). Start command `node backend/server.js`, build command `npm ci && npm run db:generate`. The Free tier is explicitly **not** recommended — its 15-minute idle spin-down and ~1-minute cold start would disrupt ImpactOne's 4 continuous background schedulers.

## PostgreSQL service
Render **Postgres**, **Basic-256mb** tier ($6/month). Real, persistent, with automatic Point-in-Time Recovery (3-day window). Upgradeable in place to Basic-1gb ($19/month) if data volume grows.

## Redis decision
**Skip at launch.** ImpactOne's backend already gracefully degrades to an uncached mode without `REDIS_URL` (verified, existing behavior — not a gap). Add Render Key Value **Starter** ($10/month, real persistence) later only if a real caching need emerges. Do **not** use the Free Key Value tier even if added, since it is in-memory-only and loses all data on every restart.

## Expected monthly cost
**$13/month** (mandatory: frontend $0 + backend $7 + database $6). **$23/month** if optional Redis is added. See `MONTHLY_COST_ESTIMATE.md` for the full breakdown and the Railway/Vercel comparisons.

## Required accounts
1. A Render account (email + payment method — required even for the free Hobby workspace tier once any paid compute service is added).
2. The existing GitHub account/repository (`cryptonfteden/ImpactOne`) — already exists, connect it to Render during service creation.
3. *(Fallback only)* A Railway account, same requirement.
4. *(Optional, if a custom domain is desired beyond Render's own subdomain)* A domain registrar account — any registrar works; Render supports bringing your own domain with automatic TLS.

## Required credentials (all must be generated or rotated by the operator — none exist yet in this environment)
- A real, freshly generated `JWT_SECRET` (≥32 random bytes, e.g. `openssl rand -base64 48`).
- **Rotated** `FINNHUB_API_KEY` and `OPENAI_API_KEY` — the currently-configured values are confirmed exposed in this repository's git history (see the immediately-preceding `REMOTE-AND-DEPLOYMENT-VERIFICATION-001` audit's `REMOTE_BACKUP_AUDIT.md`/`POST_DEPLOYMENT_RISK_REGISTER.md`). **Do not deploy with the current key values.**
- `DATABASE_URL` — auto-generated by Render when the Postgres service is created; no manual action needed beyond copying it into the backend's environment variables (or using Render's Environment Group linking).
- `ADMIN_API_KEY` — optional, only needed if admin-only routes will be reachable; generate a random value if so.
- `CORS_ALLOWED_ORIGINS` — not a secret, but must be set to the real deployed frontend origin (see deployment order below).
- `VITE_API_BASE_URL` — not a secret, must be set at frontend **build time** to the real deployed backend origin.

## Exact deployment order
1. Rotate `FINNHUB_API_KEY`/`OPENAI_API_KEY` in their respective dashboards — before touching any hosting platform.
2. Create the Render account, add a payment method.
3. Create the **Postgres** service first (so a real `DATABASE_URL` exists).
4. Create the **backend Web Service**, connected to the GitHub repo, with the build/start commands above; set `DATABASE_URL`, `NODE_ENV=production`, the new `JWT_SECRET`, the rotated provider keys.
5. Run `npm run db:deploy` against the new database (applies Prisma migrations — additive, safe).
6. Confirm `GET https://<backend-origin>/health/ready` returns `200` with `checks.database: true`.
7. Create the **frontend Static Site**, setting `VITE_API_BASE_URL` to the real backend origin from step 4 *before* the first build runs.
8. Set the backend's `CORS_ALLOWED_ORIGINS` to the real frontend origin from step 7; redeploy the backend (config-only, no rebuild).
9. Open the real frontend URL; confirm Home renders real data, and the PWA install flow resolves.
10. Follow `FOUNDER_INSTALL_GUIDE.md` for a real physical-device install/verification pass.

## Risks and limitations
- Render's Starter web-service tier has no autoscaling — a non-issue at ≤5 users, but a known ceiling if usage grows.
- Region is not changeable in place on Render once chosen — pick deliberately at setup time.
- The Railway fallback lacks bundled automatic Postgres backups; a manual backup step must be configured immediately if that path is chosen.
- This hosting decision does not close the two still-open Critical findings from the prior verification phase (unrotated exposed keys; the AI-trust reasoning-duplication defect) — those require separate, dedicated remediation and are not solved by any hosting choice.
- No CI pipeline or staging environment is included in this architecture — acceptable for a ≤5-user founder pilot per this mission's own scope, but worth revisiting before any wider rollout.

No code was modified and nothing was committed during this phase, per explicit mission instruction.
