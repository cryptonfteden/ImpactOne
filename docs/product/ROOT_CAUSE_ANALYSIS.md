# Root Cause Analysis — Every Regression Since X4

Four questions per regression, per the mission: Root Cause, Why tests missed it, Why Release Validation missed it, Permanent prevention. (Release Validation itself didn't exist until Phase X6 — for the two regressions before it existed, that question is answered as "N/A, didn't exist yet" honestly rather than skipped.)

## #5 — X4: synthetic `betaUserId` in HTTP integration tests

- **Root cause**: a copy-paste pattern. New HTTP integration tests were written by copying the calling convention from *service-level* unit tests (which call functions directly, no middleware involved), rather than the convention real HTTP tests need (a request header the `betaUserContext` middleware must independently resolve against the database).
- **Why tests missed it**: they didn't — this was caught *by* running the new tests, the same session they were written. Listed here for completeness of the "since X4" record, not as a miss.
- **Why Release Validation missed it**: Release Validation didn't exist until X6. N/A.
- **Permanent prevention**: the distinction (service tests: synthetic ids OK; HTTP tests: real persisted `BetaUser` row required) is now written into every subsequent phase's integration test files as an explicit comment, and has been followed correctly in every integration test written since (X5, X6, X7 — verified by grep this phase: every `*.integration.test.js` file's `X-Beta-User-Id` value traces to a real `betaUserRepository.createBetaUser`/`findByInviteCode` call).

## #6 — X6: `Header.jsx`'s broken import (live-broken in production since X4)

- **Root cause**: Phase X4 moved `BETA_USER_LABEL_STORAGE_KEY` from `BetaInviteGate.jsx` to `useBetaIdentity.js` as part of a real, deliberate refactor (making the identity hook the single source of truth). The refactor updated every *intended* call site but missed `Header.jsx`, which read the same constant for an unrelated purpose (displaying the beta user's label in the account menu) and wasn't part of the refactor's mental model.
- **Why tests missed it**: `Header.test.jsx` (if any existed covering this code path) or any test importing `Header.jsx` under Vitest's module resolution does not fail on a stale named import the way a bundler does — Vitest/Vite dev-server transform resolves modules more permissively in this configuration, and if no test actually asserted the specific rendered label value, the missing export's `undefined` value silently flowed through `window.localStorage.getItem(undefined)` without throwing.
- **Why Release Validation missed it**: Release Validation *found* it — it did not exist before Phase X6, and this was the very first thing its first run caught. Not a miss; this is the system working.
- **Permanent prevention**: `releaseValidation.js` now runs a real production build before every merge, specifically because dev-mode module resolution is more forgiving than a real bundler's. This is now a standing, repeatable check — not a one-time fix.

## #7 — X7: `symbolIntelligenceApi.js` never created

- **Root cause**: Phase X5's `MARKET_INTELLIGENCE_SPEC.md` documented a real migration plan for frontend consumers of the new backend `symbolIntelligenceService.js`, but the plan was written as *future* work and the phase ended without anyone building the frontend API wrapper. Phase X7 then wrote `StockSidePanel.jsx`'s migration against an import that was assumed to already exist (because the backend half was real and tested) without first confirming the frontend half existed too.
- **Why tests missed it**: `StockSidePanel.test.jsx` mocks the entire `../services/api` module (`vi.mock("../services/api", () => ({ ... }))`) — a Vitest mock replaces the module wholesale, so the test suite never actually resolves the real `symbolIntelligenceApi.js` file path. A component can import a named export from a mocked module that doesn't exist on disk, and every test still passes.
- **Why Release Validation missed it**: it didn't — `releaseValidation.js`'s build check caught it on the first `npm run build` run after the change, exactly as designed.
- **Permanent prevention**: the same standing build check as #6. The deeper prevention — never treating a documented "migration plan" as equivalent to "the file exists" — is a process note captured here, not a new automated check; no static analysis tool can verify a *plan* was actually executed.

## #8 — X7-RC: raw error-message leaks across 9 screens (this phase)

- **Root cause**: `catch (err) { setError(err?.message || "friendly fallback") }` is a natural-looking pattern that reads as "use the friendly fallback if there's no error" — but a caught JS `Error` object almost always has a truthy `.message`, so the fallback branch is dead code in practice. This exact anti-pattern was identified and named in `PRIVATE_BETA_POLISH.md` (Phase X5) — but that pass fixed it by *inspection* (reading the highest-traffic screens), not by an exhaustive search, so it only caught 3 of the 12 real instances that existed in the codebase at the time (and more were added afterward, in X6/X7 screens like `MarketPositioningScreen.jsx`).
- **Why tests missed it**: every one of these components is unit-tested with `vi.mock`, and every existing test that exercised the error path used a developer-authored `new Error("some readable string")` as the rejection — e.g. `new Error("network down")`. The test then asserted that exact readable string appeared on screen, which **the anti-pattern makes trivially true** (the raw message and the asserted message are the same string by construction). The test wasn't just insufficient — it was actively asserting the bug as correct behavior, because the mocked error was written to be readable, unlike a real backend's actual error text.
- **Why Release Validation missed it**: Release Validation checks structural things (does it build, does the backend respond, is a route protected) — it has no concept of "is this specific string shown to the user technical-sounding." This is not a gap in Release Validation's design; it's a category of check it was never meant to perform.
- **Permanent prevention**: (1) All 9 instances fixed this phase, each with its test updated to assert the *friendly* message and explicitly assert the *raw* message is absent — closing the "test asserts the bug" hole for these specific components. (2) The durable prevention is procedural: `grep -rn "\.message ||" frontend/src --include=*.jsx` (or the more targeted pattern used this phase) should be run as part of any future design/polish pass, not relied on to be caught by unit tests, which this regression proves structurally cannot catch it under the current mocking convention. (3) Recommended, not yet built: a shared `useAsyncLoad`-style hook that forces every screen to supply a static friendly-message string at the call site (making the `?.message ||` pattern impossible to write by construction) — a real, valuable follow-up outside this phase's zero-new-architecture scope.

## #9 — `portfolioEngineService.test.js`'s `getPerformanceDelta` flake (documented since ≈H2, fixed this phase)

- **Root cause**: `withMockedQuote(200)` mocked `finnhubService.getQuote` only for the duration of the order-placement call in the test; `portfolioEngineService.getPortfolioSummary` (called afterward, inside `getPerformanceDelta`) made its own independent, unmocked live call to Finnhub to mark the position to market. The test's expected `totalValue: 100000` assumed no price movement occurred between order placement and the summary read — an assumption that's false whenever the real market genuinely moved in that window.
- **Why tests missed it**: this isn't a case of tests missing a regression — it's a test with an incorrect mocking scope, present since it was written (documented as pre-existing since roughly Phase H2, per every completion report since). It was *documented*, not fixed, in H2, H3, X2, X3, X4, X5, X6, and X7 — eight prior mentions with no code change.
- **Why Release Validation missed it**: `releaseValidation.js`'s backend smoke check doesn't run the full test suite (that's `npm run test:backend`'s job, deliberately separate for speed) — but the full suite *did* catch it, every single run, and reported it accurately as a failure every time. This was never a detection gap; it was a known failure nobody had spent the time to fix.
- **Permanent prevention, and closure**: fixed this phase. `getPerformanceDelta()` is now called inside the same `withMockedQuote` scope as the order placement, so both real calls that touch a live quote are covered by one mock. Verified stable across 3 consecutive real test runs (not just one lucky pass) — and as a side effect, the test dropped from ~13-14s (real network round-trip) to ~100ms, confirming the live dependency is actually gone, not just newly lucky. This closes the one regression in this database that had gone unfixed the longest — a direct result of this phase's "keep validating until every critical user journey succeeds" mandate applying to test infrastructure too, not just UI flows.
