# APP_STORE_QUALITY.md — Phase APP-STORE-QUALITY-001

**Mission:** prepare ImpactOne for installation on a real phone. No redesign, no new functionality, no new architecture — a real-device readiness audit, with objectively verified issues fixed and everything else honestly disclosed.

**Method:** live testing via a real browser at true mobile viewports (390x844 portrait, 844x390 landscape), with fresh navigations/fresh page contexts (a stale reused page context previously produced misleading `window.innerHeight` readings in this environment — always re-verify with `page.viewportSize()` + a fresh `goto`), plus targeted source/CSS reads and `git log`. Backend (`:5000`) and frontend dev server (`:5173`) both restarted clean before testing, per this engagement's own established discipline. HEAD at session start: `61ab876` (WORLD-CLASS-FINISH-001).

## 1. Findings, fixed this phase (all objectively verified, all reproduced live before and after)

| # | Area | Finding | Verification method | Fix |
|---|------|---------|----------------------|-----|
| F1 | Touch ergonomics | The mobile Feedback widget (`.feedback-widget__toggle`) genuinely intercepted pointer events over the "For you" bottom-nav tab at 390px width — a real Playwright `click()` timed out with `"...subtree intercepts pointer events"`. A prior phase (MOBILE-FIXES-001, commit `e336923`) had already written a fix for this exact defect, but it was silently shadowed: the mobile override lived inside an earlier `@media` block in the stylesheet, while an unconditional, equal-specificity `.feedback-widget { bottom: 20px }` rule declared later in the same file always won the CSS cascade regardless of viewport width — confirmed via `getComputedStyle` reporting `bottom: 20px` at 390px width, not the intended calc(). | Real `page.click()` timeout + `getComputedStyle` before/after | Moved the real mobile override to after the base rule it needs to beat (same specificity, later in source = wins). | F2 | Touch ergonomics | Header icon buttons (alerts/notifications/quick-actions/account) measure a real 38x38px box — below Apple HIG's / WCAG 2.5.5's 44x44px recommended minimum touch target. A prior phase (WORLD-CLASS-FINISH-001) deliberately left the *visual* size at 38px because it's load-bearing for the landscape-phone header-row width calc. | Direct `getBoundingClientRect()` measurement | Added an invisible `::after` pseudo-element (`position:absolute; inset:-3px`) to `.header-icon-button`, enlarging only the **tappable hit area** to effectively 44x44px without changing the visual box, layout footprint, or the landscape width calc. Verified the 12px gap between adjacent icons leaves no overlap between neighboring tap zones, and the visual `getBoundingClientRect()` is unchanged (still 38x38). |
| F3 | Safe areas | `frontend/src/features/workspace3d/workspace3d.css`'s `.workspace3d-toolbar` (the Mission Chain button rendered over the Flagship/3D Workspace scenes) had zero `env(safe-area-inset-*)` usage anywhere, unlike every edge-pinned element in `styles.css` (header, bottom nav — 8 real usages). In portrait this scene sits below the header (which already reserves safe-area-top), but in landscape the scene can span the full available width with a device notch/pill cut into either long edge. | `grep` for `safe-area-inset` across every stylesheet — 8 matches in `styles.css`, 0 in `workspace3d.css`/`flagshipScreen.css` | Added `calc(... + env(safe-area-inset-top/left, 0px))` to the toolbar's `top`/`left`. `env()` defaults to `0px` on every device without a real inset, so this is a no-op everywhere it isn't needed and only ever adds real clearance on hardware that has a notch — zero visual change confirmed on the tested (non-notched) viewport. |
| F4 | Device rotation / install experience | `manifest.json` declared `"orientation": "portrait-primary"` — installed as a standalone PWA, this locks the app to portrait and prevents rotation entirely. Traced via `SPRINT_33_REPORT.md`: this lock was written in Sprint 33 when landscape was fundamentally broken (bottom nav didn't even render). Landscape has since been genuinely fixed (`e336923`, `fbd4a8a`) and was reconfirmed working live this session (real nav, real header row, zero overflow, in both directions of a live rotation without reload). Leaving the lock in place after fixing the underlying bug silently prevents every installed-app user from ever reaching the now-working landscape layout. | `SPRINT_33_REPORT.md` read + live before/after rotation test (portrait→landscape→portrait, no reload) | Removed the `orientation` key from `manifest.json` entirely (no lock = follows the device's natural rotation, matching the web-tab behavior that was just verified live). |

No other production code was modified. All four fixes are additive/corrective (dead-code-cascade fix, invisible hit-area expansion, additive `env()` fallback, one manifest key removed) — none change a rendered pixel on a non-affected device/orientation.

## 2. Findings, disclosed but **not** fixed (out of scope, needs real hardware, or not a defect)

- **Real notch/Dynamic Island occlusion** — cannot be verified in this environment; Chromium does not simulate non-zero `env(safe-area-inset-*)` values without real notched hardware. F3 above is a defensive, zero-risk mitigation, not a confirmed-fixed regression.
- **iOS "Add to Home Screen" splash rendering** — no explicit `apple-touch-startup-image` tags exist. Modern iOS Safari (11.3+) is documented to synthesize a splash from the manifest's icons/`background_color`, which this app already has correct values for; genuine on-device iOS behavior was not independently verifiable here. See `INSTALL_EXPERIENCE.md`.
- **Real device animation/battery behavior** (react-three-fiber's `useFrame` render loop has no explicit `visibilitychange` pause) — relies on the browser's own native `requestAnimationFrame` throttling for backgrounded tabs, which is standard and was not independently reproducible as a real battery-drain defect in this environment. Not fixed; flagged for a future real-device profiling pass, not treated as a confirmed bug.
- **Manifest install-UI screenshots** (`screenshots` array) — omitted entirely, which means Chrome/Android shows the plainer (not "rich") install prompt. Not a defect, a missing enhancement requiring real polished-UI screenshot assets; recommended, not fabricated, in `INSTALL_EXPERIENCE.md`.
- **Shared/global account state re-appearing after `localStorage.clear()`** — reconfirmed live (a genuinely fresh, cleared-storage session still lands in the same server-side Guest account with existing history). This is a long-standing, extensively-documented finding from many prior phases (identity/isolation architecture), explicitly out of scope for this mission's focus list (safe areas/rotation/touch/font-scaling/accessibility/animations/startup/splash/PWA/install/first-launch polish) and not re-litigated here.
- **Daily Feed / Home templated-explanation duplication** (identical "88% historical similarity" text/scores across unrelated events) — reconfirmed still present live. Out of scope for this mission (an AI-trust/content-quality issue, not a device-readiness issue); tracked separately under `AI_TRUST_ANALYSIS.md`/`DAILY_FEED_ROOT_CAUSE.md`.

## 3. Confirmed already-correct (re-verified live, not just assumed from memory)

- Viewport meta (`width=device-width, initial-scale=1, viewport-fit=cover`) — no `maximum-scale`/`user-scalable=no`, so pinch-zoom/accessibility zoom is never blocked.
- No `text-size-adjust`/`-webkit-text-size-adjust` overrides anywhere; no fixed `html`/`:root` `font-size` override — OS-level "larger text" scaling is not defeated by the app's own CSS.
- 200% root font-size stress test on Home (390px) produced zero horizontal overflow (`scrollWidth === clientWidth`).
- Live device rotation (390x844 → 844x390 → 390x844, **without reload**, matching a real physical rotation) produced zero horizontal overflow in either orientation and the bottom nav remained visible and correctly sized throughout.
- `prefers-reduced-motion: reduce` emulated live — app loads and renders without error.
- A real branded boot/loading state (`.boot-loading`, "Loading ImpactOne" + spinner) already replaces the old blank-white-div first paint (Phase E2) — confirmed present and rendering correctly before identity/profile resolution completes.
- Full regression: **615/615 frontend tests passing** (unchanged from baseline) after all fixes; `npm run build` completes clean (only the pre-existing, unrelated `INEFFECTIVE_DYNAMIC_IMPORT` and chunk-size warnings, identical to the pre-fix baseline build).
