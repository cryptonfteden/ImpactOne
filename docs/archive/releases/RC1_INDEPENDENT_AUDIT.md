## 3. Repository integrity — the most severe findings of this audit

**These two findings are proven with direct, unambiguous evidence — cross-referencing exactly what is committed to git against exactly what the committed code requires — not inferred from a report or a commit message.**

### 3a. A file required by already-committed code has never been committed (Critical)

`backend/services/authService.js` (committed, confirmed via `git status` showing no diff) contains `const userRepository = require("./userRepository");` at its top level. `backend/services/accountService.js` (also committed) requires it too. **`backend/services/userRepository.js` itself has never existed in git history** — confirmed two independent ways: `git log --oneline --all -- backend/services/userRepository.js` returns nothing, and `git ls-files backend/services/userRepository.js` returns nothing. It exists right now only as an untracked file on disk in this specific working tree.

**Consequence, traced through the full require chain:** `server.js` → `app.js` → `routes/index.js` (committed, unconditionally requires `authRoutes.js`) → `authRoutes.js` (committed) → `authController.js` (committed) → `authService.js` (committed) → `userRepository.js` (**does not exist in git**). A genuinely clean clone of this repository, at the current `HEAD`, would crash the entire backend process on startup with `Cannot find module './userRepository'` — not a degraded auth feature, the whole server never comes up, because Node's `require()` is resolved synchronously at module-load time as part of routing setup, before any request is ever served.

### 3b. Committed code requires three npm packages the committed manifest never declares (Critical)

`backend/services/authService.js` (committed) requires `bcryptjs` and `jsonwebtoken`; `backend/services/billing/providers/stripeBillingProvider.js` (committed) requires `stripe`. **None of the three appear in the committed `package.json` or `package-lock.json`** (confirmed via `git show HEAD:package.json` and `git diff package-lock.json` — both show these three as only-ever-uncommitted additions). They are physically present in this session's local `node_modules` (confirmed), which is exactly why every live test performed in this environment — including this session's own — cannot detect this by simply running the app locally. A genuinely fresh clone + `npm install` would not install them, and the same startup crash as 3a would occur even if 3a were somehow fixed first.

**These two findings compound: fixing only one still leaves the backend unable to start from a clean checkout.** Both are fully, honestly disclosed in the immediately preceding `RELEASE-CANDIDATE-001` phase's own `RELEASE_CANDIDATE_AUDIT.md` (it explicitly names the uncommitted `bcryptjs`/`jsonwebtoken`/`stripe` additions) — but that phase reasoned about them purely as a commit-attribution/hygiene question ("don't sweep someone else's pending change into my commit"), not as "the currently committed repository cannot start." That specific, more severe implication was not stated by that phase and is the central new finding of this one.

### 3c. 68 local commits are not backed up to the remote (High)

`git rev-list --count origin/sprint-16-live-data..HEAD` = **68** (out of 277 total commits on this branch). A real, tracked remote exists (`origin` → the real GitHub repository, confirmed via `git remote -v` and `git branch -a` showing `remotes/origin/sprint-16-live-data`) — this is not a "no remote configured" situation, it is 68 real commits' worth of work (including every fix this whole recent multi-phase arc has produced) that would be lost if this local working copy were lost, corrupted, or discarded. Per this mission's own "do not push" instruction, this was not resolved — it is reported for the user's own decision.
