## 1. Swing detection algorithms

- **What's real today:** `technicalIndicators.js`'s `detectSupportResistance()` already computes genuine local **pivot points** (a bar whose high/low is a local extreme among its 2 immediate neighbors on each side) — `recentPivotHighs`/`recentPivotLows`. Per `TECHNICAL_SIGNAL_PRIORITY.md` §3.1 (this engagement's own immediately-preceding research), this exact data is **already computed but currently discarded** by the support/resistance signal itself.
- **Central recommendation of this research: Fibonacci swing detection should reuse this exact same pivot-detection function, not build a second one.** A "swing high" and "swing low" for Fibonacci-anchoring purposes are, by definition, the same underlying concept as a support/resistance pivot point — building a separate swing-detection algorithm for Fibonacci specifically would repeat the exact kind of duplicated-detector anti-pattern this engagement has already found and corrected multiple times elsewhere (e.g., `ALGORITHMIC_ACTIVITY_RESEARCH.md` §2.12's explicit decision to make "Institutional Execution Patterns" a composite of existing detectors rather than a 15th independent one; the historical `statusTone()`/attention-threshold duplication this whole engagement's memory repeatedly cites as the anti-pattern to avoid).
- **The real, additional need beyond raw pivot detection: a significance filter.** The current pivot window (2 bars each side) finds *every* minor local wiggle, most of which are market noise, not genuine swings worth anchoring a Fibonacci retracement to. The standard, well-established charting technique for this is a **ZigZag-style filter** — only retain a pivot as a "real" swing point if the subsequent move to the *next* pivot exceeds a minimum size threshold (classically expressed as a percentage move, but this research recommends an **ATR-normalized minimum**, consistent with `TECHNICAL_SCORING_MODEL.md`'s own ATR-normalization convention, e.g. "the swing must span at least 2 ATRs" rather than a fixed percentage that doesn't adapt to the security's own volatility). This is the single most important addition this research recommends over the raw pivot data already available.
- **Multi-scale swing detection**: recommend running the ZigZag-style filter at more than one minimum-size threshold (e.g., a "minor swing" threshold and a "major swing" threshold) — a well-established practitioner distinction (some Fibonacci tools explicitly separate "minor" and "major" retracements) directly useful for `Swing Quality Score` (`FIBONACCI_SCORING_MODEL.md` §3) and for choosing which swing to anchor to when several candidates exist in the lookback window.

## 2. Automatic anchor selection

- **What's real today: a degenerate special case, not a real anchor-selection algorithm.** `analyzeFibonacci()` simply takes `Math.max()`/`Math.min()` of `high`/`low` across the last 60 bars — this happens to coincide with a genuine major swing in some cases, but has no actual logic verifying that the selected high and low form a genuine, directionally-coherent, completed swing (as opposed to, for instance, two unrelated extremes from two different, disconnected price moves that both happened to occur within the same 60-bar window).
- **Recommended selection heuristic (disclosed, hand-set, not fitted — consistent with this engagement's established convention):**
  1. Run the ZigZag-filtered swing detection (§1) to obtain a real, direction-coherent sequence of alternating swing highs and swing lows.
  2. Select the **most recent, size-qualifying swing** (the last swing-low-to-swing-high, or swing-high-to-swing-low, pair whose magnitude clears the ATR-normalized minimum) as the primary anchor pair — recency is prioritized because a Fibonacci level's practical relevance to *current* price action degrades as the anchoring swing recedes further into the past (directly informing the freshness model, `FIBONACCI_METHODOLOGY.md` §2).
  3. **Among multiple qualifying candidates within a reasonable lookback, prefer the largest-magnitude swing** (ATR-normalized) — larger, more widely visible swings are more likely to be watched by other market participants, and thus more likely for the resulting Fibonacci levels to be genuinely self-fulfilling/respected, a real, well-known practitioner rationale (not merely an aesthetic preference for "bigger is better").
  4. **The anchor pair's directional coherence must be validated** (§6, Trend Validation) — an anchor selected from a period of genuinely range-bound, low-ADX price action should be flagged as lower-quality (feeding a lower `Swing Quality Score`) even if it technically satisfies the size filter, since a "swing" during a directionless market is a materially weaker candidate than one occurring during a real, ADX-confirmed trend.

## 3. Retracement methodology

- **What's real and already correct: the standard ratio set.** `FIBONACCI_RATIOS = [0, 0.236, 0.382, 0.5, 0.618, 0.786, 1]` in `technicalIndicators.js` is exactly the conventional, industry-standard retracement ratio set (0%/23.6%/38.2%/50%/61.8%/78.6%/100% — note 50% is not a true Fibonacci-sequence-derived ratio but is universally included by long-standing market convention, and 78.6% — the square root of 61.8% — is one of two common conventions for the "deep" retracement level, the other being 76.4%; either is defensible and this research recommends keeping the current 78.6% rather than switching without a stated reason). **This is a real, credit-worthy, correct foundation — this research does not recommend changing the ratio set itself.**
- **The real gap is upstream of the ratio math, in anchor-direction determination.** The pure function's own design (`fibonacciRetracement(high, low)`, whose own comment correctly states *"the caller supplies which is which... this pure function has no opinion"*) is a genuinely good separation of concerns — the gap is that the **caller** (`analyzeFibonacci()`) never actually determines *which* direction the swing represents (an uptrend pullback, expecting support near the deeper levels, vs. a downtrend rally, expecting resistance near the deeper levels) before calling it; it always passes the window's raw max/min regardless of which occurred first. Recommend the caller determine directionality from the ZigZag-filtered swing sequence (§1-2) — if the swing low occurred *before* the swing high (a completed up-move), the retracement should be interpreted as *support levels* during an expected pullback; if the swing high occurred first (a completed down-move), the retracement should be interpreted as *resistance levels* during an expected relief rally.

## 4. Extension methodology

- **Confirmed gap: extensions do not exist at all today.** `FIBONACCI_RATIOS` stops at `1` (100%) — there is no code path anywhere computing the standard extension ratios (127.2%, 141.4%, 161.8% — the primary, most-watched extension level — 200%, 261.8%).
- **A real, important methodological distinction this research surfaces:** a retracement is a genuinely simple **2-point** measurement (a single high and a single low). A proper Fibonacci **extension**, by contrast, is conventionally a **3-point (A-B-C)** measurement: an initial swing (A→B), a retracement of that swing (B→C), and then the extension ratios project *where the next leg might reach*, measured from the A→B range but anchored at C — not simply "the same high/low pair, extrapolated past 100%." Recommend implementing extensions as a genuinely distinct 3-anchor-point methodology, reusing the same swing-detection/anchor-selection machinery (§1-2) to identify all three points (A, B, and the completed retracement's own endpoint C), rather than a naive "extend the same 2-point range beyond 100%" shortcut, which would produce a materially less standard, less-recognized set of price levels than real Fibonacci extension practice uses.

## 5. Multi-timeframe confluence

- **Directly connects to, and should directly reuse, `TECHNICAL_SCORING_MODEL.md` §2's multi-timeframe machinery** (calling the real, already-working `analyzeSymbol()`/`analyzeBars()` at more than one timeframe — e.g., daily and weekly) — this research does not recommend a second, separate multi-timeframe mechanism.
- **The specific Fibonacci concept: a "confluence zone"** — when a Fibonacci level computed on one timeframe (e.g., the daily chart's 61.8% retracement) sits very close in price to a Fibonacci level computed independently on a *different* timeframe (e.g., the weekly chart's own 38.2% retracement), the overlapping price zone is considered materially stronger, more widely watched, and more likely to produce a genuine reaction than either level would be in isolation. This is a well-established, named practitioner concept (not a novel idea introduced by this research) and is the primary input to the **Confluence Score** (`FIBONACCI_SCORING_MODEL.md` §1).
- **A real, disclosed tolerance band is required**, since two independently-computed levels will essentially never land at the *exact* same price — recommend an ATR-normalized proximity tolerance (e.g., levels within 0.5 ATR of one another count as confluent), consistent with this platform's established "express proximity in volatility-adjusted units, not a fixed price/percentage" convention (`TECHNICAL_SCORING_MODEL.md`'s own trend-strength normalization).

## 6. Confluence scoring

- **Beyond cross-timeframe Fibonacci-to-Fibonacci confluence (§5), a real, broader concept**: a Fibonacci level's credibility is further reinforced when it coincides with **other, independently-derived technical facts already computed elsewhere in this platform** — a moving average (already real: `movingAverages`/`trend`'s SMA20/50/200), a support/resistance pivot (already real, and per `TECHNICAL_SIGNAL_PRIORITY.md` §3.1, currently under-used data this research also recommends reusing here), or a round psychological price number (e.g., a level landing almost exactly on $100.00).
- **The same correlated-evidence risk this whole engagement has repeatedly identified and solved elsewhere must be guarded against here too**: several of these "independent" confluence sources are not fully independent of one another (e.g., a 50-day SMA and a support/resistance pivot may often coincide simply because both reflect the same underlying recent price history) — recommend the same disclosed, capped, diminishing-returns approach `UNIFIED_SCORING_MODEL.md` §4 and `TECHNICAL_SIGNAL_PRIORITY.md` §1 already established for cross-agent and cross-indicator agreement, applied here to avoid a cluster of correlated confluence sources inflating the score beyond what genuinely independent corroboration would support.

## 7. Trend validation

- **Directly reuses, rather than re-derives, the Technical Agent's own real trend-strength work** (`TECHNICAL_SCORING_MODEL.md` §2's `TrendScore`, including the newly-recommended real ADX-based trend-strength floor) — a Fibonacci retracement/extension computed during a period the Technical Agent's own `TrendScore` already flags as weak/directionless (a low-ADX regime) should be treated as lower-quality evidence, not validated by a second, separate trend-detection mechanism built specifically for Fibonacci.
- **The real, well-documented practitioner rationale**: Fibonacci retracement levels are meaningful specifically as *pullback/continuation* tools *within* an established trend — applying them to genuinely range-bound, directionless price action is a well-known source of unreliable signals, since there is no real directional bias for the retracement to eventually "resume."

## 8. False breakout filtering

- **Directly reuses, rather than re-implements, the Technical Agent's own real retrospective failed-breakout logic** (`analyzeBreakout()`'s genuine `FAILED_BREAKOUT` check, already credited as a real strength of this codebase in `TECHNICAL_METHODOLOGY.md` §7) — a "false breakout" of a Fibonacci level (price briefly closes beyond a key level, seeming to invalidate it, then reverses back inside) is conceptually identical to a failed range breakout, just applied to a Fibonacci-derived price level instead of a support/resistance range boundary.
- **A concrete architecture recommendation, not just a scoring one**: rather than building a *third* independent implementation of "did a level-breaking move actually hold" (support/resistance already has one, per `TECHNICAL_METHODOLOGY.md` §7/§8; a naive third Fibonacci-specific one would be a duplicate), recommend extracting the existing retrospective hold/fail-check logic into one shared, reusable helper function parameterized by "the level in question," called by support/resistance, breakout, and Fibonacci alike — directly preventing the same kind of triplicated-logic risk this engagement has repeatedly found and corrected in other parts of this codebase (e.g., the historical `statusTone()`/attention-threshold duplication, later consolidated into `claimPresentation.js`).

## 9. Summary of concrete, evidence-grounded findings driving this research's design

1. Today's Fibonacci analysis is a single, static, direction-agnostic 2-point retracement over a fixed 60-bar max/min window — a real, correct ratio set, but no genuine swing detection, anchor selection, extension levels, multi-timeframe confluence, or trend validation.
2. The exact pivot-detection data needed for real swing detection (`recentPivotHighs`/`recentPivotLows`) already exists in this codebase (in `detectSupportResistance()`) but is unused for Fibonacci purposes today — the cheapest, highest-leverage starting point, consistent with the same "reuse what's already computed" finding this engagement made for the Valuation Agent's underused Finnhub metrics and the Technical Agent's own underused pivot data.
3. Extensions require a genuinely distinct 3-point (A-B-C) methodology, not a naive extrapolation of the existing 2-point retracement math past 100%.
4. Multi-timeframe confluence, cross-indicator confluence scoring, trend validation, and false-breakout filtering should all directly reuse this platform's already-real Technical Agent infrastructure (multi-timeframe calls, ADX-based trend strength, retrospective failed-breakout logic) rather than building parallel, duplicate mechanisms specific to Fibonacci.
5. The frontend's own chart-overlay system already anticipates Fibonacci (a real, stubbed `FIBONACCI` overlay entry) but has it deliberately gated pending a separate governance approval — this research is scoped to the backend analysis architecture only, and does not take a position on that approval decision.
