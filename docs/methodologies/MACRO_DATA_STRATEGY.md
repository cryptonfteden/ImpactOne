# Macro Intelligence — Data Strategy

**Phase:** MACRO-RESEARCH-001. Companion to [MACRO_RESEARCH.md](MACRO_RESEARCH.md) and [MACRO_SCORING_MODEL.md](MACRO_SCORING_MODEL.md). Pure research — staged recommendations only, no procurement or code has occurred.

**Framing note, unique to this phase:** unlike every prior domain in this research series, the MVP tier here is mostly **wiring work, not vendor procurement** — a real, live, working data source already exists (`altDataService.getMacroData()`); the primary blocker is architectural (connecting it to `macroEconomistMember.js`), not financial (buying a new vendor relationship).

---

## MVP

1. **Wire `getMacroData()` into `macroEconomistMember.js`.** This is the single highest-leverage, lowest-cost recommendation in this entire research phase — a real, live, already-working FRED-based data source exists today and is simply not being read by the one consumer whose job is macro. This alone would close the `rates`/`inflation`/`employment`/`bonds`/`dollar` gap the member's own code comment currently discloses as missing, at effectively zero new integration cost.
2. **Add `PCEPI` (PCE) to `getMacroData()`'s existing FRED calls**, alongside the already-fetched `CPIAUCSL` (CPI) — a one-line addition to an already-working function, closing the "Fed targets PCE, not CPI" gap (§3 of the research doc) cheaply.
3. **Add one short-end Treasury series** (`DGS3MO` or `DGS2`) alongside the already-fetched `DGS10` — enables a real 10Y-3M or 10Y-2Y yield-curve-spread computation for the first time, another one-line addition to an already-working function.
4. **Add `GDPC1` (real GDP)** to the same function — the single biggest current gap (§5 of the research doc), required for a meaningful Cycle Score; disclose the estimate vintage (Advance/Second/Third) on every emission per the Scoring Model's revision-vintage discount.
5. **Migrate off the undocumented `fredgraph.csv` endpoint to FRED's officially documented, key-based REST API** (`api.stlouisfed.org/fred/series/observations`, free API key) — the current integration works today but relies on an unofficial, undocumented URL pattern; this is a real, disclosed reliability risk worth closing even though it costs nothing financially (the official API is also free).
6. **VIX, oil/gold spot prices, and credit spreads (BAA10Y) remain honestly `UNAVAILABLE` at MVP** unless a real-time market-data vendor is already reachable through this platform's existing relationships — do not approximate VIX from any proxy; report it as missing, per this whole engagement's established honesty-over-fabrication discipline.
7. **`STLFSI4` (the St. Louis Fed's own pre-built Financial Stress Index)** is a strong, cheap MVP addition for the Stress Score specifically — it is itself a FRED-hosted series, reachable through the exact same `fetchFredSeries()` mechanism already in production, requiring no new vendor relationship at all.

## Production

- **Real-time market data vendor** (for VIX, oil/gold spot/futures pricing, USD index, and daily credit-spread series if a more current source than FRED's own daily updates is needed) — recommended to **cross-reference this series' own already-completed Options Data and Algorithmic Activity research's vendor evaluations** (Databento/Massive, confirmed live and already evaluated for real-time market data in this platform's context) rather than independently re-evaluating vendors from scratch — a single real-time data relationship could plausibly serve VIX/oil/gold/USD needs alongside its existing options/equities use case, avoiding a redundant vendor relationship.
- **CME FedWatch data** — confirmed live this session as a real, well-known, free tool for market-implied Fed rate-decision probabilities (derived from 30-Day Fed Funds futures pricing) — a genuinely forward-looking complement to FRED's backward-looking series; the tool itself is delivered via an embedded third-party (QuikStrike) widget rather than an obviously simple developer API — **needs direct reconfirmation of any raw-data/API access path before procurement**, not independently verified beyond the redirect this session.
- **Finnhub's economic-calendar product** (if its exact macro-indicator coverage is reconfirmed sufficient) as a possible single-vendor alternative/supplement to direct government-source integration for release dates/figures — reusing this platform's already-configured Finnhub relationship, consistent with this whole series' repeated "exhaust an already-paid-for vendor relationship first" recommendation.
- **Widen the Fed balance-sheet/liquidity picture**: add `WALCL` (Fed balance sheet) and `RRPONTSYD` (Overnight Reverse Repo Facility usage) — both real, free, FRED-hosted, weekly-cadence series — to materially improve the Liquidity Score beyond its MVP-stage M2-only starting point.

## Enterprise

- **Graduation criteria (consistent with this whole series' "enterprise is a graduation point, not a default" framing):** move beyond FRED + a single real-time market-data vendor only once there is a demonstrated need for either (a) a dedicated economic-data terminal/vendor (Bloomberg/Refinitiv-class) for faster-than-FRED release-date alerts or deeper historical-revision archives, or (b) CME's own full licensed data feed (beyond the free FedWatch tool) for direct fed-funds-futures pricing rather than the pre-computed probability tool.
- **Do not default to enterprise tooling before MVP/Production have validated real usage and demand**, exactly as recommended for every prior domain in this research series — macro data is unusually cheap to obtain at a "good enough" quality (FRED alone covers the large majority of this research's 14 named topics for free), making a premature enterprise-tier jump even less justified here than in most of this series' other domains.

## Cross-cutting recommendations

1. **Wire the existing `getMacroData()` into `macroEconomistMember.js` before adding any new data source** — this is a strict prerequisite, not a parallel workstream; adding GDP/PCE/yield-curve data to a function that still isn't being consumed by its intended reader would not move the platform's actual macro-awareness forward at all.
2. **Never let Stress Score or Cycle Score silently substitute a partial-input result for a full one** — both must disclose exactly which named sub-inputs (STLFSI4/credit-spread/yield-curve/VIX for Stress; GDP/unemployment/yield-curve for Cycle) were actually available for a given computation, consistent with this whole engagement's honesty-over-fabrication discipline.
3. **Never conflate CFTC COT futures-positioning data (already real and live for Gold/Silver/Crude Oil/US Dollar Index) with spot/index price data for the same assets** — these are two different, real, but distinct signals and must be labeled separately, directly extending this research series' own recurring "two similar-sounding concepts, do not conflate" pattern.
4. **The Cycle Score's `cycleStage` classification must never be framed as, or compared to, an official NBER recession call** — NBER dating is a retrospective, multi-month-delayed committee judgment, not a real-time computable fact; this platform's own cycle estimate must always be presented as its own probabilistic, disclosed model.
5. **Preserve Macro's naturally market-wide (not per-symbol) architecture** — both the existing `getMacroData()` design and this whole series' just-completed Sentiment Agent precedent confirm this is the structurally correct shape for this domain; do not force a false per-symbol redesign.
