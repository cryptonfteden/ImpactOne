# Production Gaps — Agent Platform

**Phase:** PRODUCTION-READINESS-REVIEW-001. Companion to `PRODUCTION_READINESS_REVIEW.md` and `RELEASE_CHECKLIST.md` — this document is the flat, sortable gap register; the review document is the narrative evidence; the checklist is the actionable gate. Grounded in the committed history through `6cdf905` ("AGENT-SCHEDULER-001"). No code was written or modified.

| # | Area | Gap | Severity | Evidence | Agent-count sensitivity | Remediation direction |
|---|---|---|---|---|---|---|
| 1 | Scheduler / Metrics | `schedulerMetrics.js`'s `waitMsSamples`/`execMsSamples` arrays grow forever; `reset()`/`getMetrics()` never called in production | **Release Blocker** | Direct read of `recordCompleted()`; grep confirms `sharedScheduler.reset`/`getMetrics` only referenced from test files | Worsens with uptime × traffic, independent of agent count | Cap array size (ring buffer) or replace with a running-aggregate/reservoir-sampling implementation |
| 2 | Observability | `AgentExecutionLog`'s `DEFAULT_MAX_RECORDS = 5000` retention divides directly by agent count per run | **Release Blocker** | `agentExecutionLog.js`; restated from `OBSERVABILITY_AUDIT.md`, unchanged since | Directly worsens as agent count grows (~384 requests retained at 13 agents → ~50 at 100 agents) | Make retention time-based, or count executions independent of per-run agent fan-out |
| 3 | Resilience / Auth | No authentication or rate limiting on `/v2/agent-orchestrator/:symbol` or `/v2/agent-observability/:symbol` | **Release Blocker** | `agentOrchestratorRoutes.js`/`agentObservabilityRoutes.js`; `app.js` has only bare `cors()`, no auth middleware anywhere in the project | Impact scales with traffic volume, not agent count directly | Add auth middleware and/or a rate limiter in front of these routes before external exposure |
| 4 | Diagnostics | No diagnostics endpoint exists for the Agent Platform in the committed code | **Release Blocker** | Repo-wide grep for a diagnostics route; only present in uncommitted work | Compounds every other gap by making them unobservable in production | Ship a `GET` diagnostics endpoint exposing scheduler config/metrics + observability log sizes |
| 5 | Metrics | Scheduler's own rich metrics (`getMetrics()`) never exposed on any HTTP endpoint | High | Repo-wide grep for `getMetrics`/`sharedScheduler` usage outside tests | Matters more as traffic/agent count grows and operators need visibility | Expose via the diagnostics endpoint (item 4) or a dedicated metrics route |
| 6 | Configuration | Scheduler defaults are hardcoded constants with zero environment-variable overrides | High | `schedulerConfig.js`; cross-checked against `backend/config/env.js` (zero agent-platform entries) | The concurrency ceiling is the primary lever for scaling to 50/100 agents; currently requires a code change | Add env vars following the existing `env.js` pattern (e.g. `AUTONOMOUS_ENGINE_ENABLED`'s precedent) |
| 7 | Resilience | Cancellation (`cancelJob`/`cancelSymbol`) not reachable via HTTP; abandoned requests hold a scheduler slot until natural timeout/retry completion | High | `agentOrchestrator.js`'s `run()` accepts no `signal`; self-disclosed in `AGENT_SCHEDULER.md` | Impact grows with real-world client disconnect frequency, which scales with traffic, not directly agent count | Accept an `AbortSignal` in `run()`, wire it to the Express request's `close`/`aborted` event |
| 8 | Logging | Zero `console.*`/logger calls anywhere in `agentScheduler`/`agentOrchestrator`/`agentObservability` | High | Direct grep across all three subsystem directories | Makes incident reconstruction impossible at any agent count once traffic is real | Add structured log lines for timeouts, retries, cancellations, failures |
| 9 | Health | `systemHealthService.js` (the platform's one general health endpoint) has zero Agent Platform awareness | High | Direct grep of `systemHealthService.js` | Matters most once the Agent Platform is a production-critical dependency, independent of agent count | Add a scheduler-saturation/registry-status check into the existing health aggregation |
| 10 | Observability | `agentOrchestratorController.js` discards `correlationId` before responding to the HTTP caller | High | Controller source; restated from `OBSERVABILITY_AUDIT.md`, unchanged | Not agent-count sensitive; matters for any traceability at any scale | Include `correlationId` in the JSON response body or a response header |
| 11 | Observability | `runObserved()` has no try/catch around `agentOrchestrator.run()`; request-level failures produce zero execution-log record | High | `observableOrchestrator.js`; restated from `OBSERVABILITY_AUDIT.md`, unchanged | Not agent-count sensitive | Wrap the call, log a request-level failure record on early throw |
| 12 | Scalability | The "global" concurrency pool is global only per-process; no shared coordination layer exists across instances | High | No Redis/queue dependency in `package.json`; `sharedScheduler` is a plain in-process singleton | Becomes the dominant risk specifically at the 100-agent target, where horizontal scaling is the natural capacity response | Either commit to single-instance deployment, or introduce a shared coordination layer (e.g. Redis-backed semaphore) before scaling horizontally |
| 13 | Scheduler | Cancelled executions reported as generic `status:"error", error:"CANCELLED"`, indistinguishable from a real agent bug in aggregate metrics | Medium | `failureTaxonomy.js` has no `CANCELLED` code; self-disclosed in `AGENT_SCHEDULER.md` | Not agent-count sensitive | Add a `CANCELLED` failure code |
| 14 | Metrics | Both metrics systems (`metricsCollector.js`, `schedulerMetrics.js`) compute simple arithmetic means only, no percentiles | Medium | Direct source read of both files | Increasingly misleading as agent count/variance grows | Add p50/p95/p99 computation |
| 15 | Deployment | No graceful shutdown (`SIGTERM`/`SIGINT`) anywhere in `backend/server.js`; all Agent Platform state is in-process memory only | Medium | Grep of `server.js`; confirmed no persistence layer for scheduler/observability state | Impact (lost in-flight work, lost history) scales with traffic and deploy frequency | Add shutdown handling that drains in-flight work / persists critical state before exit |
| 16 | Scheduler | `ExecutionQueue.dequeue()` is an O(n) linear scan for highest effective priority | Low | `executionQueue.js`; explicitly disclosed as a future upgrade path | Only matters if queue depth reaches the thousands | Replace with a binary heap if/when real queue depth warrants it |
| 17 | Registry / Scalability | The 100-agent scenario has never been exercised against real, independently-slow agents — only reasoned about via unit tests with synthetic delays | Low (verification gap, not a code defect) | Registry is 3 real agents + 10 near-instant honest stubs; no load test exists in the repo for this subsystem | Directly relevant to the mission's "100 agents" question — the answer today is analytical, not empirical | Build a synthetic slow-agent load test before committing to a 100-agent production target |
