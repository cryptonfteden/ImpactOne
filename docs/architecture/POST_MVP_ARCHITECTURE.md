# ImpactOne Agent Platform — Post-MVP Architecture Review

**Phase:** POST-MVP-ARCHITECTURE-001. Documentation only — no production code was modified. Grounded in a fresh, direct source read of the current registry, the Unified Stock Intelligence engine, `scoringVocabulary.js`, 2 of the 13 domain agents' actual `confidenceModel.js` files, the Agent Scheduler's real post-hardening state, the provider registry, and a repo-wide grep confirming the Claim Intelligence Layer's real production-call-site count — not assumed from prior session summaries alone.

**Headline verification of the mission's own framing claim** ("all Intelligence Agents are implemented except the News Agent"): **confirmed accurate.** `registry.js` registers 14 agents; direct inspection confirms 13 are real (Technical, Options, Sentiment [market-wide], Symbol-Sentiment [per-symbol], Short Interest, Earnings, Valuation, Fibonacci, Insider, ETF Flow, Institutional, Macro, Analyst Consensus) and exactly 1 (`newsAgent.js`) remains an honest stub, with its own comment explaining precisely why: *"newsService.getNews(query) exists but is query-scoped, not symbol-scoped analysis with a confidence/direction — wiring it in honestly requires a real per-symbol relevance/analysis layer this codebase doesn't have yet."*

## 1. Unified Stock Intelligence architecture

**Genuinely well-built, and the single strongest architectural artifact reviewed this session.** `unifiedStockIntelligenceEngine.js`'s own header comment states its design constraint precisely: *"this engine selects its three target agents from the live registry... and executes them through the exact same `runObserved()` seam every other real request already uses... No duplicate scheduling/execution logic exists in this file."* Verified true by direct read — it imports the unmodified `agentOrchestrator`, the real `runObserved()` (Scheduler + Observability), and composes normalization/conflict-detection/aggregation/case-building as separate, single-purpose modules (`agentDirectionMapper.js`, `conflictDetector.js`, `weightedAggregationEngine.js`, `caseBuilder.js`, `keyDriversBuilder.js`).

**A genuinely good, rare cross-phase discipline was independently confirmed**: `agentSelector.js`'s `TARGET_AGENT_IDS` list has been incrementally, correctly updated by **6 separate subsequent phases** (Sentiment → Insider → ETF Flow → Institutional → Short Interest → Macro → Analyst Consensus), each phase's own commit adding itself to the list with a dated, attributed comment explaining exactly why. This is the opposite of the duplication/drift pattern found repeatedly elsewhere in this engagement's history — a genuine positive to preserve, not a coincidence.

**But a real, concrete integration gap exists**: `TARGET_AGENT_IDS` currently reads `["options", "earnings", "valuation", "symbol-sentiment", "insider", "etf-flow", "institutional", "short-interest", "macro", "analyst-consensus"]` — **`technical` and `fibonacci` are both absent**, despite both being real, per-symbol-relevant, already-registered agents. Root cause (inferred from commit ordering, not confirmed by a code comment): `technical` predates the Unified engine's own initial 3-agent scope (Options/Earnings/Valuation) and was simply never added afterward; `fibonacci`'s own implementation phase did not update `agentSelector.js` the way every other phase since has. **This is the single most concrete, cheapest-to-fix "missing abstraction" finding in this whole review** — two of the platform's most foundational technical-analysis signals are silently absent from its own "unified" per-symbol report.

## 2. Agent interaction model

**The single most important, decisive finding of this entire review.** This engagement's own prior `AI-CORE-001-REVIEW` phase found the real, excellent Engine→Bus→Claim pipeline (`intelligenceBusService.js`, `claimFormationService.js`, `claimConfidence.js`, `claimLifecycle.js`) had **zero production callers**, only test-file callers, and explicitly flagged this as a disclosed, correctly-labeled "foundation, not yet live" state at that time (when only 3 real domain agents existed).

**A repo-wide grep this session confirms this is still true today, now with 13 real domain agents built since**: `intelligenceBusService.publishEvent` appears in exactly 4 files, and **all 4 are test files** (`uiIntegration.integration.test.js`, `claimFormationService.test.js`, `intelligenceBusService.test.js`) — **zero production call sites exist anywhere in `backend/services/domainAgents/`** (confirmed via a direct grep across the entire domain-agents tree, zero matches for `intelligenceBusService`, `publishEvent`, or `claimFormationService`).

This means the platform currently has **two entirely separate, non-overlapping agent-interaction models** operating side by side:
1. **The Agent Orchestrator's own real `detectConflicts()`/`computeOverallConfidence()`** (the original AGENT-ORCHESTRATOR-001 mechanism, already flagged in this engagement's own `UNIFIED-SCORING-RESEARCH-001` for its naive raw-string-equality direction comparison), reused directly by the Unified Stock Intelligence engine's own `conflictDetector.js`/`weightedAggregationEngine.js`.
2. **The Claim Intelligence Layer** (confidence-vs-probability separation, dominance caps, lifecycle, governance) — architecturally superior in every dimension this engagement has independently verified, but genuinely unused by any of the 13 real agents.

Every one of this engagement's 13 domain-research phases (Options through Analyst Consensus) recommended, in its own scoring-model document, that its outputs flow into `DecisionTrace.evidenceReferences`/the Claim Layer — **none of them actually do, today.** This is not a contradiction of those research docs' own recommendations (which were never implemented as code by this reviewer, per every phase's "Do NOT write production code" constraint) — it is a genuine, disclosed gap between design intent and shipped reality that this review is the first to confirm precisely, with an exact grep-verified call-site count.

## 3. Provider abstraction quality

The provider registry (`providerRegistry.js`) has grown from the previously-confirmed 15 registered providers to **22** — 7 new since the last review (`finvizProvider`, `tipranksProvider`, `zacksProvider`, `spdrProvider`, `cftcCotProvider`, `coinglassProvider`, `optionsFlowProvider`). The underlying contract (`baseProviderContract.js`'s `validateProviderShape`, `honestStubFetch` for unconfigured providers) remains sound and consistently applied — every provider this review spot-checked (`tipranksProvider.js`, confirmed this engagement's own recent Analyst Consensus research) still follows the same honest, disclosed-`configurationRequirement` pattern established in Sprint 37.

**A real, structural gap**: this registry is a flat array with no tiering by data-cost, licensing-status, or freshness-tier — a caller cannot ask "give me only the real, configured providers" without filtering `PROVIDERS` manually. As the registry approaches 30+ entries (a plausible near-term trajectory given this engagement's own research-series pace), a flat array with no queryable metadata layer (real/stub/enterprise-only, cost tier, freshness class) will become a genuine discoverability problem.

## 4. Shared scoring consistency

**A second decisive, concretely-verified finding.** `scoringVocabulary.js` — this platform's own explicitly documented *"single documented scoring contract... the one source of truth for evidence quality"* (Sprint 18A) — currently contains exactly **12** `SCORE_DEFINITIONS` entries (`confidence`, `conviction`, `quality`, `risk`, `relevance`, `sourceCredibility`, `evidenceFreshness`, `evidenceAgreement`, `uncertainty`, `optionsAnomalyConfidence`, `marketSentimentComponentConfidence`, `marketSentimentOverallConfidence`). **None of the ~10 domain agents built since the Market Sentiment Engine phase (AI-ENGINE-002.1) added a single new entry here**, despite every one of this engagement's own research-series scoring-model documents (Valuation, Institutional, Insider, ETF Flow, Short Interest, Macro, Analyst Consensus, Fibonacci) explicitly proposing new named scores as candidate `SCORE_DEFINITIONS` entries.

Confirmed via direct source read of 2 real `confidenceModel.js` files (each of the 13 domain agents has its own, in `backend/services/domainAgents/<agent>/confidenceModel.js`):

- **`institutionalAgent/confidenceModel.js`**: `BASE_AVAILABLE = 30`, `MAX_COVERAGE_BONUS = 25`, `MAX_COMPARABLE_BONUS = 20`, `MAX_CONVICTION_BONUS = 15`, `STRUCTURAL_SCOPE_PENALTY = 10` — a disclosed, hand-set 5-component additive formula unique to this agent.
- **`macroAgent/confidenceModel.js`**: `FRED_WEIGHT_TOTAL = 70`, `PROXY_WEIGHT_TOTAL = 30` — a completely different concept (pure data-source-availability weighting, no coverage/conviction concept at all), unique to this agent.

Both are individually well-documented, honestly disclosed (neither fabricates a value when data is unavailable), and internally consistent — **this is not a dishonesty finding.** But confirmed via a repo-wide grep: **zero references to `scoringVocabulary.js` or `claimConfidence.js`'s `MAX_SINGLE_EVIDENCE_WEIGHT` dominance-cap constant exist anywhere in `backend/services/domainAgents/`.** Each of the 13 real domain agents independently reinvented its own confidence formula from scratch, rather than registering a new entry in the one canonical registry this platform's own architecture explicitly designed for exactly this purpose. This is the scoring-formula-level instance of the same "duplication despite good individual design" pattern this engagement has repeatedly found at the frontend-component level (`statusTone`/`attentionLevel`, now confirmed again here at the backend confidence-formula level).

## 5. Confidence calibration consistency

Directly downstream of §4's finding: with 13 independently-designed confidence formulas, **there is no way today to compare "Institutional confidence: 62" against "Macro confidence: 58" and know whether they mean the same thing** — they are computed from entirely different input sets with entirely different weighting philosophies. `scoringVocabulary.js`'s own already-disclosed limitation (*"confidence, conviction, and modelConfidence are currently the same underlying number under three names... pending real calibration data"*) was written when only the original Recommendation Engine existed; it has not been revisited to address the now much larger problem of 13 mutually-incomparable per-agent confidence scales.

This is not a new problem this review invented — it is the direct, larger-scale consequence of a real, disclosed decision (each agent phase computing its own confidence conservatively and honestly) made 13 times independently without a shared calibration contract enforcing comparability.

## 6. Registry scalability

Unchanged in kind from this engagement's own prior `AGENT_ORCHESTRATOR_STRESS_AUDIT.md`/`PRODUCTION_READINESS_REVIEW.md` findings, now confirmed to still apply at 14 agents (up from 13): the registry (`registry.js`'s `ALL_AGENTS` array, `agentOrchestrator.js`'s internal `Map`) remains a plain in-process, per-process singleton with **no Redis/shared-state dependency anywhere in this repo** (previously confirmed, not re-verified live this session but no architectural change has occurred to alter this). Horizontal scaling would still silently fragment the registry across processes exactly as previously documented.

## 7. Scheduler scalability

**Genuine, verified progress since the last review.** `PLATFORM-HARDENING-001` (confirmed via direct source read this session) resolved several real gaps `PRODUCTION_READINESS_REVIEW.md` previously flagged: `schedulerConfig.js` now reads real `process.env` overrides (no longer 100% hardcoded); a real `/api/v2/agent-diagnostics` endpoint exists and is tested (`agentDiagnostics.integration.test.js`); `X-Correlation-Id` is genuinely honored and echoed back verbatim, confirmed by a real, passing integration test (`agentObservability.integration.test.js`).

**One previously-flagged item requires re-verification, not yet fully re-confirmed clean this session**: `schedulerMetrics.js`'s `waitMsSamples`/`execMsSamples` arrays are still unconditionally `.push()`-appended in `recordCompleted()` with no visible in-file cap; a `reset()` function exists and is confirmed called from within `agentScheduler.js` (line 286) — but this session did not confirm whether that call site is a genuine periodic/bounded-growth safeguard or only a narrower reset path (e.g., test teardown or a specific lifecycle event). **Recommended as the first item to directly re-verify** before either closing or re-opening the prior unbounded-memory-growth finding.

## 8. Observability completeness

The Agent Observability layer (`agentExecutionLog.js`, `metricsCollector.js`, `executionTimeline.js`) remains real and correctly scoped to per-agent execution history, distinct from the Scheduler's own separate `schedulerMetrics.js` (queueing/concurrency/retry mechanics) — a correct separation of concerns, previously confirmed and unchanged. The new `/v2/agent-diagnostics` endpoint (confirmed real this session) appears to be the first genuine consolidated read-surface bridging both — a positive step toward closing the previously-flagged "no single operator-facing view of platform health" gap.

**A new observability gap, specific to the now-13-real-agent scale**: none of the 13 domain agents' own internal sub-computations (e.g., Institutional's 5-component confidence breakdown, Macro's FRED-vs-proxy availability split) are exposed through the shared Observability layer — each agent's own `confidenceModel.js` returns a rich `components` object (confirmed in the Institutional example above), but this structured detail is only visible to a caller who already knows to look inside that specific agent's own response shape, not through any shared, agent-agnostic diagnostic surface.

## 9. Extension points

The `createStubAgent()`/`agentInterface.js` contract (metadata/execute/confidence/health) remains a genuinely clean, proven extension point — 13 consecutive phases have each successfully upgraded a stub to a real implementation "in place" (same id, same slot), with zero registry-id conflicts across the whole series. `alertTypeRegistry.js` and `overlayRegistry.js` (frontend-adjacent extension points, previously reviewed) remain sound precedents of the same registered-but-`implemented:false` pattern this backend series has also used successfully.

**The one extension point that has not kept pace**: `agentSelector.js`'s `TARGET_AGENT_IDS` (§1) is a manually-maintained list, not itself a registry-driven default (e.g., "include every registered agent unless explicitly excluded") — this is precisely why `technical`/`fibonacci` could silently fall through the cracks; a registry-driven inclusion-by-default (with an explicit exclusion list for the deliberately-excluded market-wide `sentiment` id) would make this class of gap structurally impossible rather than merely unlikely.

## 10. Long-term maintainability

The platform's single greatest maintainability asset remains its **consistent per-agent internal structure**: every one of the 13 real domain agents follows the identical file-naming convention (`<agent>Agent.js`, `confidenceModel.js`, `aiSummary.js`, a data-provider file, and 1 file per named analytical signal, each with a co-located `.test.js`) — this is a genuine, valuable, load-bearing convention that materially lowers the cost of onboarding a 14th/15th real agent (News, and whatever comes after it). The risk is that this same discipline has **not yet been extended one level up** — to the shared scoring/confidence/Claim-Layer integration layer (§2, §4, §5) — meaning the *shape* of each agent is consistent, but the *meaning* of each agent's own headline confidence number is not.

| **Production blockers** | None identified as strictly blocking at today's usage scale — every gap found this session is a real, disclosed design/consistency gap, not a crash-risk or data-integrity risk |
